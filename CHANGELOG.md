## 1.2.4 - 2026-11-26

**Upgrade: 1.2.3 and earlier can report Red Hat Enterprise Linux, Rocky Linux
and AlmaLinux systems as clean.**

- A package installed from a module stream got none of the CVEs Red Hat has not
  fixed for that stream, and the run read as complete. A UBI 8 image with
  `nodejs:22` showed 19 of its 70; Red Hat lists 88 such streams for RHEL 8 and
  28 for RHEL 9, `postgresql`, `php`, `nginx` and `mariadb` among them.

Check again any system of these distributions that uses module streams and was
judged by an earlier version.

What changes for scripts, besides the findings:

- A package built for a module and given without its stream (`name@version`,
  `--packages-from`, or a purl or SBOM without the modularity label) now exits 2
  as incomplete.

## 1.2.3 - 2026-11-26

**Upgrade: 1.2.2 and earlier can hide unfixed CVEs on Red Hat Enterprise
Linux, Rocky Linux and AlmaLinux.**

- A CVE without a fix was left out of a package when another package of the same
  release, in the same run, had an answer for it. With an old `openssl` beside
  it, `compat-openssl11` lost 49 of them.
- On Red Hat Enterprise Linux and AlmaLinux, a fix built for a module stream was
  applied to packages installed outside the module, which read as affected: 266
  findings on an AlmaLinux 8 image with Perl.

Check again any system of these distributions judged by an earlier version.

What changes for scripts: unfixed CVEs that were hidden now appear and the
module findings are gone, so `--fail-on` may give another result. A package
version typed without its module marker is read as one outside the module.

## 1.2.2 - 2026-11-26

**Upgrade: 1.2.1 and earlier can report vulnerable systems as clean.**

- On Debian, Ubuntu, Alpine and openSUSE, a binary name given without its
  source package (`libssl3` as `name@version`, in a purl or in an SBOM) found
  nothing, and a run of names alone read as complete. A Syft SBOM of a Debian
  12 image showed 27 of its 242 findings.
- A Red Hat Enterprise Linux, Rocky Linux or AlmaLinux image scanned from a
  host outside that family got none of the CVEs Red Hat has not fixed, and read
  as complete: a UBI 9 image showed none of its 476.
- On a host of that family, or with `--distro`, an image of another release got
  the unfixed CVEs of the wrong release.
- The `apk` components of an SBOM were not checked; they were listed as
  unresolved.
- A purl lost its epoch outside Fedora, so patched CVEs were reported as
  affected.

Check again any SBOM, package list or container image judged by an earlier
version.

What changes for scripts, besides the findings:

- A name given without its source package, which OSV holds no advisory under,
  now exits 2 as incomplete on Debian, Ubuntu, Alpine and openSUSE, even if it
  is a package that never had one.
- The JSON `provenance` of Debian and Ubuntu hosts and containers reads
  `package_db` where it read `user_input`.
- A run over several Red Hat family releases downloads the unfixed list of each.

## 1.2.1 - 2026-11-26

**Upgrade: 1.2.0 and earlier can report vulnerable systems as clean.**

- On Red Hat Enterprise Linux 10 no advisory was found, and every host and
  image read as clean and complete.
- On Rocky Linux a subpackage such as `openssl-libs` hid the CVEs filed under
  its source package, and the run read as complete.
- On Debian, Alpine, openSUSE and Red Hat Enterprise Linux, a release OSV holds
  no data for read as clean and complete. Ubuntu was already checked in 1.2.0.
- Rocky Linux and AlmaLinux hosts and containers were not recognised.
- An advisory naming hundreds of CVEs took gigabytes of memory. openSUSE kernel
  updates name up to about 500: on Leap 15.6 with the kernel it shipped with,
  1.2.0 passes 8 GB and aborts. Earlier releases were not measured.

Check again any Red Hat Enterprise Linux 10 or Rocky Linux system that was
judged clean by an earlier version.

What changes for scripts, besides the new findings:

- A release OSV has no data for now exits 2 as incomplete.
- RHEL 10 is judged by its minor release: `--distro rhel:10` without one exits
  2 (use `rhel:10.2`, for example), and `host.os_version` reads `10.2` where it
  read `10`.
- A Rocky Linux package given without its source (`name@version`, a purl or
  `--packages-from`) now exits 2 as incomplete.
- A run whose reader stops early (`| head`) now ends with its own exit code and
  no message, where it exited 70.

## 1.2.0 - 2026-11-25

**Upgrade: 1.1.0 and earlier can report vulnerable systems as clean.**

- On an Ubuntu interim release (25.10 or 26.10, for example) no advisory was
  found at all, and the run read as clean and complete (since 0.0.5).
- On distributions judged through OSV, an advisory covering several packages
  could give one package the fix of another. The report showed a fix that does
  not exist, or dropped the CVE as patched (since 0.1.0).
- `--fail-on` with a severity level could exit 0 over many findings, because
  the severity was not read on Debian, Ubuntu, Alpine and openSUSE, and only in
  part on Rocky Linux.

Check again any host that was judged clean by an earlier version.

What changes for scripts: an interim release past its support, and a release
OSV has no data for, now exit 2 as incomplete; many findings that were
`unknown` now carry a severity, so `--fail-on` may fail where it passed; and a
warning on stderr says how many findings it still cannot judge.

## 1.0.0 - 2026-11-24

The first stable release. The contract of 1.0.0-rc.1 stands unchanged: the JSON
output (schema version 1), the exit codes, the configuration keys and the
flags are the contract for the 1.x series (see the support policy). Libraries
are published too and carry no API promise.

Since 1.0.0-rc.1:

- The `--help` text and the errors about options, input files and
  configuration values follow the locale (English and Brazilian Portuguese).
  The messages clap prints for a mistyped command line and those of the
  libraries stay English.
- `--help` and the man page list every supported distribution.
- `url` is updated to 2.5.9 (RUSTSEC-2026-0592), in the project and in the
  fuzz crate.
- Dependencies: `clap`, `clap_complete`, `clap_mangen`, `rusqlite` 0.43 and
  `jiff` 1.0; the publisher of `jiff` is trusted in cargo-vet.

1.0.0 is released before two items of the roadmap that were meant to precede
it: a second maintainer with release permission, and an independent security
review. Both are still open and are listed as such in the roadmap and in
GOVERNANCE.md.

## 1.0.0-rc.1 - 2026-11-17

The release candidate of 1.0. No code changes since 0.5.0: the version is the
contract, frozen and tested (see the support policy), published so that it can
be tried before it is final. Libraries are published too and carry no API
promise. It changes before 1.0.0 only if the candidate shows a mistake in the
contract, and this file will say so. 1.0.0 waits for the people items of the
roadmap.
